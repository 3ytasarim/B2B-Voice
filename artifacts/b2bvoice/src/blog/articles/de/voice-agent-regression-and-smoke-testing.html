Automatisierte Regressions- und Smoke-Tests für Sprachagenten: ein praktischer Leitfaden

Von B2B Voice

Ein automatisierter Regressionstest für Sprachagenten prüft, ob eine neue Version Verhalten beschädigt hat, das zuvor funktionierte. Setzen Sie Smoke-Tests für Sprachagenten für eine kurze Reihe kritischer Pfade ein, gezielte Regressionsfälle für die jeweilige Änderung und kontrollierte Audio- oder Telefontests, wenn der Nachweis von einem echten Anruf abhängt. Ein simulierter Kalender kann zeigen, welche Argumente der Agent übermittelt hat. Ein Anruf über die vorgesehene Route kann zeigen, ob die anrufende Person die Bestätigung gehört hat und ob die Mitarbeitenden die Übergabe erhalten haben.

B2B Voice richtet individuelle Implementierungen an den Workflow und den Release-Verantwortlichkeiten des Kunden aus. Für ein Team mit Terminplanung kann dazu gehören festzulegen, wer ein Deployment stoppen darf, welche Ergebnisse einen Release blockieren und wie die Mitarbeitenden mit Buchungen umgehen, die nach einem Rollback noch offen sind.

Wichtigste Erkenntnisse

  • Versionieren Sie die Einstellungen, die das Verhalten verändern können, darunter Prompt, Modell, Workflow, Stimme, Tool-Vertrag und Route.
  • Wählen Sie Tests danach aus, was sich geändert hat und was die verfügbare Testoberfläche überprüfen kann.
  • Bewahren Sie bei einem instabilen Test den vollständigen Ergebnisverlauf auf. Untersuchen Sie folgenreiche Inkonsistenzen vor dem Release.
  • Weisen Sie Canary, Rollback und offenen Transaktionen jeweils eine klare Verantwortung zu.

Die Test-Suite auf die Änderung abstimmen

Eine Smoke-Suite fragt, ob der wesentliche Pfad weiterhin startet und abschließt. Eine Regressions-Suite fragt, ob ein früherer Fehler oder ein erforderliches Verhalten nach einer Änderung zurückgekehrt ist. Derselbe Buchungsfall kann beiden Zwecken dienen, wenn er einen kritischen Pfad durchläuft. Ein Release, der durch eine Änderung des Kalenderschemas ausgelöst wird, braucht außerdem Fälle, die gezielt das Schema, das Retry-Verhalten und die Rückmeldung (Read-back) herausfordern.

Führen Sie ein Release-Manifest für Prompt, Modell, Stimme, Spracheinstellungen, Tool-Schemas, Anwendungsadapter, Workflow, Daten-Fixture und gegebenenfalls die Telefonie-Konfiguration. Ein Provider-Alias kann gleich bleiben, während sich die zugrunde liegende Implementierung ändert. Halten Sie die Version fest, die der Dienst preisgibt, und vermerken Sie, wo Sie keine beobachten konnten. Halten Sie eine frühere funktionierende Baseline zugänglich, damit ein verändertes Ergebnis untersucht werden kann.

Die Testautomatisierung für Sprachagenten funktioniert am besten, wenn die Suite zeigen kann, welche Änderung sie abfangen soll. Ein großer, undifferenzierter Durchlauf kann länger dauern und die Ursache eines Fehlers schwerer erkennbar machen. Dokumentieren Sie, welche Prüfungen übersprungen wurden, und halten Sie erforderliche Nachweise am Release-Gate sichtbar.

Wissen, was jede Testoberfläche belegen kann

Ein Mock kann auf Abruf einen Fehler zurückgeben, eine Anfrage erfassen und eine deterministische Assertion deren Argumente prüfen lassen. Die Mock-Werkzeuge der Python-Standardbibliothek unterstützen das Setzen von Seiteneffekten und das Untersuchen von Aufrufen. Ein Mock folgt nur dem Vertrag, den Sie ihm gegeben haben. Wenn der echte Adapter ein Datum oder eine Fehlerantwort anders interpretiert, können Test und Implementierung für sich genommen beide gesund wirken. Dokumentation zu Python unittest.mock

Ein Sandbox-Vertragstest kann den tatsächlichen Integrationsclient gegen isolierte Testdaten ausführen. Nutzen Sie ihn für Antwortstruktur, Berechtigungen, Zustandsänderungen und Abgleich. Ein Audio-Replay prüft, was ein Modell oder Agent unter kontrollierten Bedingungen erhalten und zurückgegeben hat. Wenn behauptet wird, dass eine anrufende Person oder ein Mitarbeitender die Route nutzen kann, führen Sie einen autorisierten Anruf über den vorgesehenen Telefonpfad durch und holen Sie den Nachweis vom Empfänger ein. Der Leitfaden zu IVR und Telefonrouting zeigt, welche Beobachtungen zu Route und Übergabe Sie festhalten sollten.

Legen Sie bei nichtdeterministischen Gesprächen zulässige Ergebnisse und die erforderliche Bedeutung fest. Eine höfliche Ablehnung kann verschiedene Formen annehmen. Ein verbotener Schreibzugriff muss unabhängig von der Formulierung verboten bleiben. Vergleichen Sie Kandidat und Baseline mit derselben Fallfamilie und denselben Einstellungen, und behalten Sie alle Versuche. Nutzen Sie versionierte Ergebnis-Fixtures, damit ein geändertes Skript oder eine geänderte Erwartung nicht als veränderter Agent erscheint.

Ein lauffähiger Regressionstest für eine unklare Buchung

Dieses Python-Beispiel verwendet nur die Standardbibliothek und Test-Doubles. Speichern Sie es als test_booking.py und führen Sie python -m unittest test_booking.py aus. Die Namen der Beispiel-Adapter gehören zur Fixture. Der Test führt keine Netzwerkaufrufe aus und verwendet keine Produktionsdaten.

import unittest
from unittest.mock import Mock


def reserve_with_readback(calendar, request_id, slot):
    try:
        calendar.reserve(request_id, slot)
    except TimeoutError:
        # The save might have committed before the reply timed out.
        pass

    saved = calendar.lookup(request_id)
    if saved and saved["request_id"] == request_id and saved["slot"] == slot:
        return "confirmed"
    return "pending"


class BookingRegression(unittest.TestCase):
    def setUp(self):
        self.calendar = Mock(spec=["reserve", "lookup"])
        self.calendar.reserve.side_effect = TimeoutError("fixture timeout")
        self.request_id = "fixture-booking"
        self.slot = "thursday-east-morning"

    def test_readback_can_confirm_a_committed_booking(self):
        self.calendar.lookup.return_value = {
            "request_id": self.request_id,
            "slot": self.slot,
        }
        outcome = reserve_with_readback(
            self.calendar, self.request_id, self.slot
        )
        self.assertEqual(outcome, "confirmed")
        self.calendar.reserve.assert_called_once_with(self.request_id, self.slot)
        self.calendar.lookup.assert_called_once_with(self.request_id)

    def test_wrong_booking_stays_pending(self):
        self.calendar.lookup.return_value = {
            "request_id": self.request_id,
            "slot": "friday-west-afternoon",
        }
        outcome = reserve_with_readback(
            self.calendar, self.request_id, self.slot
        )
        self.assertEqual(outcome, "pending")
        self.calendar.reserve.assert_called_once_with(self.request_id, self.slot)

    def test_no_record_stays_pending(self):
        self.calendar.lookup.return_value = None
        outcome = reserve_with_readback(
            self.calendar, self.request_id, self.slot
        )
        self.assertEqual(outcome, "pending")
        self.calendar.reserve.assert_called_once_with(self.request_id, self.slot)

Im fiktiven Fall kann ein externer Dienst die Buchung gespeichert haben, bevor seine Antwort in ein Timeout lief. Ein einzelner Schreibversuch mit anschließender übereinstimmender Rückmeldung (Read-back) erlaubt die Bestätigung. Ein fehlender oder widersprüchlicher Datensatz hält den Workflow im Wartezustand. Der Code bildet providerspezifische Retries, verzögerte Konsistenz, Abfragefehler, Zugriffskontrollen oder Telefon-Audio nicht ab. Für diese Verhaltensweisen braucht eine Implementierung eigene Tests. Ein Test-Adapter kann den erwarteten Datensatz liefern, während ein echter Kalender einen anderen zurückgibt. Ergänzen Sie einen Sandbox-Read-back, bevor Sie sich in einem Release auf die Integration verlassen.

Einen Trace für eine Unterbrechungsregression aufbewahren

Ein Gesprächsprotokoll kann zeigen, dass der Agent eine vollständige Antwort erzeugt hat, obwohl die anrufende Person unterbrochen hat, bevor sie sie hörte. Markieren Sie in einem Audio-Regressionstest die neue Äußerung der anrufenden Person, den Punkt, an dem die Wiedergabe stoppte, und die darauffolgenden Ereignisse. Wenn der Agent weitersprach, prüfen Sie, ob er die alte Bestätigung fortsetzte oder auf die Korrektur einging. Ein Anruf über die vorgesehene Route ist nötig, wenn Gateway-Pufferung oder ein Empfänger verändert, was die anrufende Person hört.

Vergleichen Sie Kandidat und Baseline unter derselben Aufnahmebedingung und denselben Operator-Einstellungen. Akzeptieren Sie bei Fällen mit variierender Formulierung die erforderliche geschäftliche Bedeutung und prüfen Sie die geordneten Seiteneffekte unabhängig davon. Ein erwarteter Trace kann verlangen, dass eine Korrektur vor einer Ersatzaktion eintrifft, ohne das Modell bestimmte Worte erzeugen zu lassen. Berichten Sie alternative Gründe, warum erwartete Ereignisse fehlen können, darunter eine abgebrochene Aufnahme oder ein Anruf, der vor der Korrektur endete.

Halten Sie Artefakte zugriffsbeschränkt und schwärzen Sie nicht erforderliche Payloads. Aussagekräftige Nachweise bei instabilen Tests sichern

Ein instabiler Test kann bestehen und fehlschlagen, ohne dass sich der erwartete Release ändert. Achten Sie auf gemeinsam genutzte Sandbox-Datensätze, Abhängigkeiten von der Uhrzeit, uneinheitliche Telefonpfade, Modellvariation und Agent-Einstellungen, die nicht erfasst wurden. Die pytest-Dokumentation nennt unkontrollierten Systemzustand und mangelnde Isolation als häufige Ursachen instabiler automatisierter Tests. Wiederholen Sie den Lauf, um die Bedingungen zu untersuchen. Behalten Sie den ursprünglichen Fehlschlag in den Unterlagen. pytest-Hinweise zu instabilen Tests

Wenn eine unwesentliche Formulierungsprüfung instabil ist, geben Sie ihr eine verantwortliche Person und eine zeitlich befristete Entscheidung, während das Team den Test repariert. Eine instabile Autorisierungs- oder Duplikat-Schreibprüfung sollte ein Release-Thema bleiben, bis das betreffende Verhalten verstanden ist. Automatisierte QA für Sprach-KI braucht eine klare Möglichkeit, fehlende Nachweise zu kennzeichnen. Ein sauberer Abschlussbericht nach einem Wiederholungslauf kann nicht belegen, was bei einem fehlgeschlagenen Versuch geschehen ist.

Canary-Traffic sollte eine verantwortliche Person, bekannte Routen und einen stabilen Vergleich haben. Proben Sie, wie das Team das Senden neuer Anrufe an den Kandidaten stoppt, laufende Sitzungen beibehält oder auslaufen lässt und den Endzustand bereits begonnener Aktionen verifiziert. Das Site Reliability Workbook von Google beschreibt, wie sich Teil-Releases gegen Kontrollgruppen bewerten lassen. Stellen Sie den erwarteten Serviceweg wieder her und gleichen Sie den Geschäftsdatensatz ab, bevor Sie die Wiederherstellung als abgeschlossen markieren. Google-SRE-Hinweise zu Canary-Releases

Nutzen Sie den Leitfaden zum Testen von Sprachagenten im Produktivbetrieb für die Grundabdeckung über Fehlermodi hinweg. Nutzen Sie den Vergleich von Retrieval und Tool Calling, wenn Sie entscheiden, ob eine Änderung eine Wissensantwort, eine externe Aktion oder beides betrifft.

Release-Gates festlegen, die ein Testverantwortlicher deuten kann

Legen Sie fest, ob jede Prüfung blockierend, beratend oder wartend auf Nachweise ist, bevor der Kandidat läuft. Eine blockierte Prüfung der Buchungsintegrität sollte erkennbar sein, selbst wenn eine Prüfung der Sprachqualität gut aussieht. Ein fehlender Trace zum Ziel sollte die Übergabe-Behauptung offen lassen. Geben Sie der verantwortlichen Person für den Release einen Link zum genauen Ereignis und eine unabhängige Möglichkeit, den resultierenden Datensatz einzusehen, wenn die Entscheidung von einer Integration abhängt. Das hilft auch der Person in Bereitschaft, ein Anwendungsproblem von einem Runner-Problem zu unterscheiden.

Manche Testwerkzeuge für Sprachagenten können Modellgespräche erneut abspielen und Text vergleichen. Prüfen Sie, welche Werkzeuge tatsächliches Audio verarbeiten und welche die Gegenseite eines Anrufs beobachten können. Halten Sie diese Grenzen im Ergebnis ausdrücklich fest, damit ein automatisierter Testlauf für Sprachagenten nicht stillschweigend eine gestufte Routenprüfung ersetzt.

Wenden Sie dieselbe Disziplin auf das Rollback an. Wenn die gewählte Version wiederhergestellt ist, aber ein verzögerter Vorgang weiterhin wiederholt wird, ist der Vorfall für diesen Geschäftsdatensatz weiterhin aktiv. Prüfen Sie, dass die vorherige Route neue Anrufe erhält, ermitteln Sie alle Arbeiten, die an den zurückgezogenen Release gebunden sind, und gleichen Sie den Endzustand ab, bevor Sie den Vorfall schließen.

Die Prüfungen einbeziehen, die ein Operator nach dem Rollout braucht

Eine verantwortliche Person für den Release sollte wissen, welche Version einen gemeldeten Vorfall bearbeitet hat und welche Fixture ihn reproduzieren könnte. Führen Sie ein lesbares Run-Manifest mit der Kandidatenversion, der Anrufroute, der betroffenen Abhängigkeit und einem genehmigten Verweis auf das Ergebnis. Wenn ein Problem Daten betraf, die ein breiter Personenkreis nicht sehen sollte, halten Sie die Grenze des Ereignisses fest und stellen Sie zugrunde liegende Nachweise nur der autorisierten prüfenden Person zur Verfügung. Reproduzieren Sie das Problem mit einem erfundenen Fall, bevor Sie es in die laufende Suite aufnehmen.

Häufig gestellte Fragen

Worin unterscheidet sich ein Smoke-Test von einem Regressionstest?

Ein Smoke-Test prüft, ob ein wesentlicher Pfad nach einer Änderung funktioniert. Ein Regressionstest prüft Verhalten, das korrekt bleiben muss, oft einschließlich eines bekannten früheren Fehlers. Ein kritischer Buchungs- oder Übergabefall kann zu beiden Mengen gehören.

Kann ein Mock belegen, dass eine Telefonübergabe funktioniert?

Ein Mock kann das Zielargument und die Reaktion der Anwendung auf ein simuliertes Ergebnis verifizieren. Bestätigen Sie die Übergabe auf der autorisierten Telefonroute, indem Sie die Annahme am Ziel und das Zwei-Wege-Audio beobachten.

Sollte ein späterer Erfolg einen früheren fehlgeschlagenen Lauf aufheben?

Bewahren Sie beide Ergebnisse auf. Ein sporadischer Fehler kann im Produktivbetrieb relevant sein. Klären Sie, ob die Abweichung vom Test, von der Umgebung, von einer Abhängigkeit oder vom Agenten stammte, bevor Sie die Release-Entscheidung ändern.

Was sollte ich nach einer Prompt-Änderung ausführen?

Beginnen Sie mit den betroffenen Richtlinien- und Bestätigungsfällen. Ergänzen Sie Regressionsfälle für bekannte Fehler sowie Audio- oder Telefontests, wenn die Änderung Unterbrechungen, das Verständnis der anrufenden Person oder Übergaben beeinflussen kann.
