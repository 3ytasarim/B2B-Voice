How to Test IVR and Conversational Voice AI Systems

By B2B Voice

Interactive voice response testing checks whether a caller can enter through a real phone path, choose or describe the right option, and reach the intended destination or an approved fallback. A keypad event, a correct speech classification, and an accepted transfer request are intermediate signals. For a handoff that should reach billing, verify the answered destination, two-way audio, and any context the receiving team needs. When the queue is closed, verify the business action the fallback promises.

In a custom voice workflow, B2B Voice scopes the existing phone number, the routes the business can control, and the handoffs staff can actually receive. A route that technically connects to the wrong office or into an unstaffed queue leaves the caller with the same unresolved problem.

Key takeaways

  • Test traditional IVR menus and conversational IVR speech paths against the same business routing rules.
  • Capture the digit, recognized intent, selected branch, queue disposition, and destination evidence separately.
  • Exercise invalid input, silence, timeouts, closed queues, and failures on the transfer leg.
  • Inspect the backend record when a fallback promises a ticket or callback.

Build a route inventory before placing a call

IVR stands for interactive voice response. A traditional IVR may play prompts, collect touch-tone input, and route callers through a defined tree. A conversational IVR can interpret spoken requests and ask a clarifying question before choosing a route. They can coexist on a single phone line. A caller could press a digit to choose a language, describe an invoice issue in speech, and finish with a person in the billing queue. The comparison of IVR and AI voice agents explains where each approach fits.

Inventory the published phone number, the initial carrier or private branch exchange (PBX) route, forwarding rules, menu version, departments, business hours, and designated owners. For each branch, record the destination during business hours and the fallback after hours. A shared national number can route a caller to an office using a different time zone. Test the office’s actual local hours and holiday exceptions. The test should also account for an unexpected dialed or forwarded number wherever the deployment exposes that information.

Separate signaling, input, and media

Session Initiation Protocol (SIP) can establish, modify, and terminate a session. A signaling response can show that a call was established at a particular hop. The receiving side may still have silence, one-way audio, or the wrong prompt. Inspect signaling and media independently on the relevant call legs. IETF RFC 3261

Dual-tone multi-frequency (DTMF) is the familiar touch-tone keypad input. A route can carry those tones in-band as audio or convey named telephone events in Real-time Transport Protocol (RTP). Check which mode the actual endpoints negotiated. When using RTP events, inspect the event identity and end marker rather than counting each packet as a separate keypress. A trace that contains the correct digit still needs to show how the menu interpreted it. IETF RFC 4733

A caller who presses an unmapped key needs a different test from a caller who says nothing. Test invalid input, no-input handling, and the wait before each timeout. The World Wide Web Consortium (W3C) VoiceXML specification distinguishes events for no input and input that fails to match. A modern route can apply the same distinction even when it uses another implementation. Test repeated failures and verify that the route eventually reaches the business’s approved fallback. W3C VoiceXML 2.0

Decide what to assert for keypad and speech routes

For a fixed menu version, send the expected key sequence and assert the exact branch, prompt, and destination for that path. Check menu traversal with both complete and interrupted input. In an automated IVR testing harness, keep sent digits, call events, and listener evidence in the same case record. A menu recording can sound correct even when the digit selects a stale destination.

Spoken routing accepts several phrasings. “There’s a charge I don’t recognize” and “Can someone explain my invoice?” may both belong to billing in a fictional test tenant. Use scripted phrases, natural paraphrases, and variations in audio quality. For ambiguous speech such as “I need help with my account,” define when the agent should ask a follow-up. Evaluate which destination was eventually reached and whether a clarification was appropriate. A model’s chosen classification alone leaves both questions open.

In voice bot testing, compare the route selected during a dialogue replay with the route observed on a controlled call. A voicebot testing solution can report which destination the agent chose, while the telephony owner verifies the actual forwarding and queue path. Use conversational AI testing for language behavior and direct assertions for observable route, transfer, or ticket outcomes.

Check the input at the menu boundary

Repeat a path with input during the greeting and with input after the prompt completes. The correct behavior depends on whether the route supports early input and when it starts listening. In a controlled call, observe what the input receiver saw and which menu state was active. A valid digit sent before input collection began may never reach the intended branch.

Document where prompts come from and whether the receiving party heard the current version. A cached or misrouted greeting can tell callers to press a key that now belongs to another department. The menu test should compare the instructions the caller heard with the active routing behavior.

Verify the destination after a transfer

Use the evidence the transfer method exposes

Some SIP deployments use the REFER method to ask another component to initiate a referred action. Where applicable, subsequent status notifications can describe how that action progressed. A transfer may also be handled by a telephone platform that creates and bridges another leg without exposing REFER to the article’s reader. Identify the deployed method before deciding which events must appear. IETF RFC 3515

Resolve the intended queue or person, correlate the original leg with the outbound leg, and verify who or what answered. An answering system can produce a connected event when the workflow requires a person. Listen or use a controlled receiving observer to establish two-way media. For a warm transfer, verify that the receiving agent gets the approved context and that the caller remains connected through the introduction. For a blind transfer, be clear about how the original system learns that the destination failed, if it receives that information at all.

Check the receiving workflow

Consider a fictional multi-location property service desk. A caller in a different time zone calls the main number for a building in Phoenix. The voice route correctly identifies maintenance but transfers to a closed queue that still plays a greeting. The carrier shows an answer. An actual employee was never available to respond.

The relevant test crosses more than the IVR. It needs the resolved building, destination schedule, queue disposition, and, if the caller accepts a callback, a real sandbox task in the correct office. Include a receiving-team check that the task contains only the facts needed to continue. If the service provides no callback outside staffed hours, the response should explain the available path clearly.

Test what happened at the transfer edge

A route can look correct in a recording played back from the originating side even when the receiving side heard silence. Verify both directions with an observer at the approved endpoint. During a warm transfer, confirm that any private staff briefing ended before the customer joined, if that is how the workflow is configured. During a failed transfer, verify whether the caller returns to the original agent, enters another queue, or hears an actionable callback choice. An event on the first leg cannot settle how the second leg behaved.

For AI voicebot testing, repeat the same destination check when you change a voice prompt or the carrier route. Changes that leave the dialogue policy intact can still alter when a greeting begins or whether the agent receives keypad input. An operations owner can use the matrix to choose the evidence required from each change.

Keep call traces usable for operations

Record the menu or prompt version, privacy-safe call reference, time zone, route choice, transfer legs, destination status, and resulting business record. Separate call termination from a successful handoff. A caller may hang up because the queue is busy, after hearing what they need, or before the route is resolved. Mark the last observed stage and avoid assigning a reason the logs cannot establish.

Use the same evidence sequence when comparing keypad and speech paths. A faulty configuration can affect both routes even when language evaluation looks good. The guide to failures, fallbacks, and human handoff covers how to define recovery behavior. A separate controlled voice load test can check the already verified route when traffic changes.

Test an integration failure as part of the call

Give the sandbox callback system a controlled failure mode. A promised callback should require the destination’s task receipt. If the service times out, the agent should explain the pending or alternate state the workflow allows. Check for a duplicate task when the integration is retried. Keep the route decision, transfer result, caller-facing message, and final task status in the same case record. Each helps a different team repair the failure.

Frequently asked questions

Can a keypad menu and a conversational voice agent share the same phone number?

Yes. A call can use keypad input for a predictable choice and move to a conversational agent for a spoken request. Test the transition, destination, and fallback as one route.

Does an accepted transfer request prove that a person answered?

A request acceptance shows that a component accepted the transfer request. Verify the subsequent leg, the intended destination’s answer, and usable media where the workflow requires them.

How do I test after-hours IVR routing?

Set up a controlled call that matches the office’s local hours or holiday schedule. Verify that it avoids a closed queue and follows the promised alternative. Check the saved task if a callback is offered and accepted.

What should I capture when callers hang up in the queue?

Record the last observed stage, queue disposition, disconnect, and any authorized backend action. Keep abandoned calls separate from successfully answered transfers.
