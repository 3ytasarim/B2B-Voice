Voice Agent Evaluation Data: How to Build Reliable Test Datasets

By B2B Voice

Reliable voice agent evaluation data describes the caller’s situation, what the agent is allowed to do, and what the business system should show after the call. A conversation script alone leaves too much open. The same closing sentence can accompany a successful reservation, a failed request, or a record saved under the wrong location. A useful test case can distinguish those outcomes.

B2B Voice scopes custom voice agent implementations around decisions the customer’s staff already make. During scheduling discovery, that might mean defining when a request remains pending, when it becomes a booking, and which office owns an unresolved call. Those distinctions give an evaluation dataset its expected outcomes.

Key takeaways

  • A fixture needs initial state, caller intent, allowed actions, and an independently verifiable outcome.
  • Synthetic callers are useful for controlled variation. Consented human recordings add natural timing, delivery, and acoustic conditions.
  • Keep related speakers, scripts, and incident-derived examples together when creating dataset splits.
  • Record label policies, data rights, and changes alongside the cases themselves.

Design scenarios around a business decision

Start with what staff must resolve

Well-designed voice agent test datasets map the decisions a business wants the agent to make. For an office scheduling workflow, those decisions may include finding an available slot, confirming the office and time zone, updating a permitted appointment, withholding restricted information, and routing a caller to staff. Each scenario should name the starting state and the actions the caller has authorized. Start with ordinary calls, then include mistakes and ambiguous cases that make the workflow expensive to repair.

Define voice agent ground truth before a candidate responds. Separate what an annotator can hear from facts known only to the simulation. A caller might say “Thursday,” while only the fixture specifies that the East office is closed Thursday. Record spoken information as speech evidence, and use the seeded calendar to define which actions are available. Otherwise the evaluator may expect the agent to infer facts that the caller or integration never supplied.

Define several valid paths when the workflow allows them. One agent might confirm the caller’s time zone immediately. Another might establish the location first and confirm the same slot afterward. Both can pass if they preserve the required facts, respect the same authorization rule, and finish with the expected record. When exact wording matters, such as distinguishing a request from an approved confirmation, document the meaning the response must communicate.

Make the outcome oracle independent

An outcome oracle describes the evidence that decides whether a test passed. For a case that checks how a voice agent updates a CRM or calendar, use a read from the sandbox calendar to check a booking, the approved queue event to check a transfer, or an ordered write log to check that the system never touched a prohibited record. An HTTP success response or a statement in the transcript can support the investigation. The oracle should use the observation closest to the actual consequence.

The final record can also hide an intermediate mistake. An agent might book the first date, then delete it after the caller corrects the request. A test that only sees the final appointment may pass even though the earlier action triggered staff notifications. Keep forbidden operations and duplicate writes in the evidence requirements. B2B Voice Evaluation Dataset Design Framework

Design and review decisions for an evaluation dataset
Design decision What to capture Review question
Scope Caller intent, the business owner, workflow version, and permitted actions. Could someone who did not write the case explain what the test proves?
Starting state Appointment, location, account authority, hours, and integration behavior relevant to this case. Can the runner recreate the state for another release?
Dialogue and audio conditions Caller wording, meaningful corrections, pauses, noise, channel, and language where relevant. Does the case sample the intended behavior without introducing irrelevant variation?
Ground truth Caller-confirmed entities, permitted reply meanings, and the approved set of actions. Can reviewers distinguish ambiguity from an incorrectly captured value?
Business oracle Independent final state, action history, and prohibited events. Would the test catch a false confirmation or a duplicate write?
Provenance and maintenance Source type, rights, reviewer decision, split, case version, and owner. Can the team reproduce or retire the case without guessing who supplied it?

Treat this framework as a contract between whoever authors a case and whoever reads its result. A developer may know why a webhook failed. An operations owner supplies the distinction between a booking that exists and a callback that has merely been requested. Review those decisions together before collecting more audio.

Give an evidence gap its own outcome

If the test runner loses a tool trace, the evaluator may still be able to verify the final record. The same run cannot verify that the agent avoided a write to the superseded date. State which evidence is mandatory, which observation can substitute for it, and who resolves an inconclusive case. Otherwise a missing artifact can be mistaken for a clean action history.

For changes that affect release decisions, record the case version and the rule version separately. A business may intentionally change what a callback ticket must contain. Replaying old dialogue against the new contract can be useful, but retain the previous expectation when comparing historical results.

A fictional evaluation case in JSON

This fixture describes a caller correcting the day before the agent writes. All identifiers, dates, and records are invented. The reply expectation deliberately accepts several ways to explain a confirmed result. The business outcome still requires a row in the sandbox calendar, and the history must show no write to the superseded slot.

{
  "test_case_id": "east-office-correction",
  "scenario": "The caller requests Friday, pauses, and confirms Thursday.",
  "language": "en-US",
  "caller_intent": "book an appointment",
  "initial_context": {
    "customer_id": "fixture-caller",
    "calendar_id": "sandbox-east",
    "confirmed_candidate": "2030-06-13T10:00:00-04:00",
    "superseded_candidate": "2030-06-14T10:00:00-04:00",
    "existing_reservation": null
  },
  "audio_conditions": ["telephone audio", "pause before correction"],
  "expected_entities": {
    "location_id": "east-office",
    "confirmed_slot": "2030-06-13T10:00:00-04:00"
  },
  "expected_tool_calls": [
    {
      "operation": "create_reservation",
      "fixture_arguments": {
        "calendar_id": "sandbox-east",
        "slot": "2030-06-13T10:00:00-04:00"
      }
    }
  ],
  "expected_spoken_answer": "Confirm the Thursday booking only after read-back.",
  "expected_business_outcome": "The sandbox calendar contains the confirmed reservation.",
  "prohibited_actions": ["reserve Friday", "create a duplicate reservation"],
  "acceptance_criteria": [
    "The saved appointment matches the confirmed slot and office.",
    "The action history contains no write to the Friday slot.",
    "The caller hears a confirmation only after the result is verified."
  ]
}

Define whether the expected calls are required, optional, or forbidden. The fixture above requires a reservation write to the confirmed slot and can permit a lookup before that write. The operation name is a fictional fixture label. Map it to the actual sandbox adapter when implementing a runner. Apply a versioned schema to check the required fields and types. A JSON Schema validator can check the shape of the file. A separate workflow assertion must check whether the appointment exists under the right calendar identity. JSON Schema Draft 2020-12

Create companion cases with the same caller intent and different initial states. When the slot is unavailable, the expected state may be a declined write and an offer of another appointment. When a confirmed request times out, the expected next step may be a read-back tied to the original operation. Reusing the same sentence across those cases reveals whether the agent reads system state or repeats a familiar answer.

Choose inputs that represent the calls you care about

Combine different data sources with a clear test purpose

Synthetic voice data is useful for holding the wording constant while changing noise, pacing, or interruptions. A scripted synthetic caller can exercise larger groups of conversation test cases consistently. Give the caller simulator only the facts the role would know. A simulator that knows the intended answer or sees a hidden calendar result may rescue the agent in ways a real customer could never reproduce.

With appropriate permission, commission human recordings to add natural repairs, variable speech rate, different devices, and speakers’ ordinary pronunciation. Replay representative cases over a controlled phone route when the release decision depends on what reaches a real telephone endpoint. A quiet studio recording and a real call under a poor connection exercise different parts of the system.

For production-derived scenarios, prefer an incident pattern rebuilt with fictional identities and newly written dialogue. Keep the part that drove the problem, such as a correction after a long pause or a second person with a similar name. Avoid carrying original audio or private text into a fixture pipeline without explicit authority, verified access, and a retention plan. The guide to privacy-preserving evaluation covers the record copies that teams need to account for.

Use published datasets for the tasks they were designed to support

SLURP pairs spoken English material with intent and entity annotations. It can help a reader understand how a spoken-language understanding dataset represents a single request. A single-turn example leaves the effects of a network handoff or transactional read-back outside the test. FLEURS supplies parallel read-speech material across languages, which is useful for comparable phrases and speech recognition research. A read passage does not represent spontaneous call repair. Check the rights for the exact subset and modality before reuse. A paper describing voice agent benchmark data does not automatically authorize commercial redistribution of its audio or recordings. Review rights for each input and each use

Before reusing public or commissioned material, identify the audio, transcript, annotations, and any model or generated voice used to make it. Check whether the terms permit internal testing, commercial use, modification, and redistribution for each item you plan to use. Keep the version and evidence of consent or permission with the dataset record. If the terms only authorize a narrower use, commission your own fixture or link to the publication without republishing its samples.

Treat voice AI test data generation as a separate source type in the dataset. Version the generator instructions, settings, and audio transformations. If a release check depends on an actor’s specific pronunciation, freeze that recording so later generations do not quietly change the test. Preserve speaker or actor groups when sampling a holdout.

Protect the holdout and maintain the case record

Split voice AI evaluation datasets by the source of similarity. Keep paraphrases of the same script, repeated takes by the same actor, and variants from one incident on the same side of the split whenever they would reveal the behavior the holdout is meant to test. A different filename or synthetic voice can still carry nearly identical content. If prompt development can see a benchmark’s exact examples, record that exposure and reserve independent cases for release decisions. For public benchmarks, document what you know about training or tuning overlap and leave uncertainty visible where the provider’s training data is unknown.

Write an annotation guide with acceptable paraphrases, critical fields, and a state for unresolved meaning. Have a second reviewer check consequential or disputed cases. A caller who never confirmed an address belongs in an ambiguity case. A case in which a field was clearly spoken but omitted belongs in a recognition or state-handling case. The two may produce the same empty slot and still need different repairs.

Give each fixture a stable identifier and version the initial state, intended labels, rights, and any audio transformation. Keep enduring failure cases in a regression dataset that can feed automated regression and smoke tests. Refresh the coverage set when call mix, products, business hours, channels, or languages change. A new service area can introduce unfamiliar addresses and different routing rules even though the old tests still pass. Record that distribution shift alongside the new cases. The datasheets approach provides a model for documenting composition, collection, intended uses, and maintenance. Gebru and colleagues

Frequently asked questions

How is an evaluation dataset different from a transcript archive?

An evaluation dataset specifies the allowed actions, expected state, evidence, and access rights for each test. An archive can preserve historical material without supplying those decisions or granting permission to reuse it.

Can synthetic callers replace consented human recordings?

Synthetic callers are useful for controlled variations and repeatable fixtures. Realistic pacing, live telephone behavior, overlapping speech, and speaker variation need evidence that resembles the intended caller population and channel.

What if several different agent replies are acceptable?

Specify required meaning and prohibited promises. Use independent assertions for the resulting state and any write history. Let the agent choose a natural phrasing or clarification path that meets those conditions.

Should regression cases be removed when the bug is fixed?

Keep important cases while the workflow and risks still apply. Retire them with a documented reason when their policy or integration becomes obsolete. Preserve the version associated with past test results.
