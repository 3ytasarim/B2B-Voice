RAG vs. llamadas a herramientas vs. contexto del prompt: cómo los agentes de voz con IA acceden al conocimiento del negocio y a datos en vivo

Cuando un agente de voz responde una pregunta sobre el negocio, lo importante no es simplemente si «sabe» la respuesta. Lo importante es de dónde procede, qué tan actualizada está esa fuente y si es la fuente autorizada para esa pregunta concreta.

Publicado el 30 de agosto de 2026~15 min de lecturaIA de voz · RAG · Datos del negocio
Respuesta rápida

Un agente de voz con IA puede obtener información de cuatro lugares distintos: el conocimiento previo del modelo, el contexto del prompt o de ejecución, el conocimiento de la empresa recuperado y los sistemas de negocio en vivo. Estas fuentes no son intercambiables. RAG sirve para encontrar documentos relevantes; las API en vivo suelen ser más adecuadas para obtener el estado actual y autorizado, como la disponibilidad del calendario o el registro de un cliente.

Cuatro fuentes distintas pueden estar detrás de una misma respuesta hablada

«La IA conoce nuestro negocio» suena sencillo, pero oculta varios mecanismos técnicamente distintos. Un agente de voz en producción puede responder una pregunta a partir de instrucciones colocadas directamente en su contexto de ejecución, responder otra a partir de un documento de políticas recuperado y responder una tercera solo después de consultar un calendario o un CRM.

Esas fuentes tienen fortalezas, modos de fallo y propiedades de confianza diferentes. Tratarlas como una única «base de conocimiento» indiferenciada genera errores evitables.

Modelo conceptual de B2B Voice: ¿de dónde viene la respuesta?
1. Conocimiento del modeloLo que el modelo base aprendió durante el entrenamiento.
2. Contexto del prompt y de ejecuciónInstrucciones, estado de la conversación y pequeños datos explícitos suministrados en tiempo de ejecución.
3. Conocimiento recuperadoPasajes relevantes encontrados en documentos externos o en contenido indexado.
4. Estado en vivo y autorizadoDatos actuales leídos de un CRM, un calendario, un sistema de pedidos, una base de datos u otro sistema de origen.

Este modelo de cuatro capas es un marco de ingeniería, no un estándar de API. Aun así, se corresponde bien con el comportamiento que exponen los sistemas de producción actuales. La API de Retrieval de OpenAI, por ejemplo, realiza búsqueda semántica sobre datos externos, mientras que su flujo de llamadas a funciones separa la salida del modelo de la ejecución de código en el lado de la aplicación.12

Principio fundamental

Saber no es hacer. Encontrar una política de reembolsos es un problema de conocimiento. Comprobar si el cliente 48121 ya recibió un reembolso es un problema de estado actual. Emitir un reembolso es un problema de acción.

1. Conocimiento del modelo: útil y amplio, pero no es su fuente de verdad privada

Un modelo de lenguaje llega con capacidades generales e información aprendida durante el entrenamiento. Eso puede ser útil para la comprensión del lenguaje, el razonamiento, la terminología habitual y el contexto general del mundo. No debe tratarse como una fuente autorizada para datos privados del negocio o que cambian con rapidez.

Un modelo base no sabe automáticamente lo que ocurrió en su CRM hace cinco minutos. No sabe de forma inherente qué horarios de cita están libres esta tarde, si una factura concreta está pagada o si su empresa cambió ayer la política de cancelación. Si la aplicación no ha suministrado esa información mediante contexto, recuperación o una integración con un sistema en vivo, no debe suponerse que el modelo la posee.

Es una cuestión de procedencia de los datos. El conocimiento del entrenamiento y el estado privado en tiempo de ejecución son capas de información distintas.

2. Contexto del prompt y de ejecución: lo mejor para información pequeña, explícita y relevante para la sesión

El contexto del prompt o de ejecución es la información que se entrega directamente al modelo para la sesión actual. Puede incluir el rol del agente, el tono, las reglas del negocio, el estado de la conversación, el nombre verificado de la persona que llama, el idioma seleccionado o un conjunto reducido de datos lo bastante estables como para suministrarlos directamente.

Por ejemplo, un agente de voz podría recibir:

  • «Eres el asistente de recepción de Northside Dental.»
  • «No diagnostiques afecciones médicas.»
  • «El nombre verificado de la persona que llama es Maria.»
  • «La oficina cierra los domingos.»
  • «Pide confirmación antes de crear una cita.»

El contexto del prompt resulta atractivo porque es directo: no hay paso de recuperación ni consulta externa que esperar. Pero se convierte en una mala fuente de verdad cuando los equipos empiezan a copiar en el prompt grandes conjuntos de datos operativos que cambian con frecuencia. El inventario, los saldos de los clientes, la disponibilidad de citas y el estado de los pedidos cambian de forma independiente a la sesión del modelo de lenguaje.

Este último punto es una recomendación de ingeniería y no una regla universal: use el contexto del prompt para instrucciones compactas y datos específicos de la sesión; prefiera lecturas de sistemas autorizados para el estado operativo en vivo.

3. RAG: recuperar el conocimiento relevante antes de responder

La generación aumentada por recuperación (RAG) es un enfoque en el que la aplicación recupera información relevante de fuentes de conocimiento externas y se la proporciona al modelo como contexto para su respuesta.

La API de Retrieval actual de OpenAI lo describe como búsqueda semántica sobre sus datos. La búsqueda semántica puede mostrar resultados conceptualmente similares aunque la consulta y el documento compartan pocas palabras clave exactas, o ninguna. Los resultados de la búsqueda pueden incluir fragmentos relevantes, puntuaciones de similitud y el archivo de origen.1

Un flujo de recuperación habitual tiene este aspecto:

DocumentosPolíticas, preguntas frecuentes, manuales, información de productos
→

→

→

RespuestaGenerar a partir de la evidencia recuperada

RAG es especialmente útil cuando la respuesta está en documentación demasiado extensa o cambiante para pegarla en cada prompt: políticas de reembolso, descripciones de servicios, catálogos de productos, procedimientos internos, condiciones de garantía o preguntas frecuentes específicas de cada sede.

Pero los detalles concretos —tamaño de los fragmentos, modelo de embeddings, método de ranking, búsqueda híbrida, reordenamiento (reranking) y comportamiento de la indexación— son decisiones de implementación. La documentación de OpenAI es un ejemplo de un sistema de recuperación actual, no una definición que toda arquitectura RAG deba seguir.

La recuperación semántica no es lo mismo que una consulta exacta de un registro

Esta distinción es una de las decisiones de diseño más importantes en la IA de voz para empresas.

La recuperación semántica responde a una pregunta de relevancia: ¿Qué pasaje se relaciona más con lo que preguntó la persona que llama? Una consulta exacta al sistema responde a una pregunta de estado: ¿Qué dice actualmente el registro autorizado?

Si un registro exacto de un CRM o de una base de datos está disponible mediante una API adecuada, usar la similitud semántica aproximada como sustituto de esa consulta introduce una incertidumbre innecesaria. Es una inferencia de ingeniería respaldada por la diferente mecánica de la recuperación y de las llamadas a funciones, no un requisito de ningún proveedor.

Error frecuente

«Una base de datos vectorial es básicamente el CRM de la IA». No. Un almacén vectorial es útil para recuperar por similitud semántica. Un CRM es un sistema operativo con registros específicos, permisos, identificadores, flujos de trabajo y estado transaccional actual.

RAG tiene una variable oculta: la actualidad de los datos

Un sistema de recuperación puede encontrar el documento correcto y, aun así, devolver una respuesta desactualizada.

Supongamos que una empresa tiene dos documentos de política de cancelación. El más antiguo dice que los clientes pueden cancelar hasta 24 horas antes de una cita; el más reciente dice 48 horas. Un recuperador puede considerar ambos documentos semánticamente relevantes. Si la estrategia de indexación y de metadatos no distingue la política vigente de la obsoleta, la relevancia de la recuperación por sí sola no puede establecer cuál debe regir la respuesta.

La versión preliminar de Azure AI Search de Microsoft en 2026 convierte la actualidad de los datos en una preocupación explícita de la recuperación. Su recuperación sensible a la actualidad puede inclinar el ranking hacia los documentos más recientes, aunque Microsoft señala que la actualidad sigue siendo una señal de ranking y no un filtro estricto: los documentos más antiguos aún pueden aparecer cuando son muy relevantes.3 Es una función específica de un proveedor, pero ilustra un punto general: la relevancia y la vigencia son dimensiones distintas.

Modelo de confianza en el conocimiento de B2B Voice

Para las respuestas en producción, conviene plantearse cuatro preguntas independientes: relevancia de la recuperación, autoridad de la fuente, actualidad de la fuente y fidelidad de la respuesta. Una puntuación de similitud alta responde solo a la primera de ellas.

DimensiónPregunta que hay que hacerseEjemplo de fallo
Relevancia de la recuperación¿Encontramos contenido relacionado con la pregunta?Un fragmento irrelevante de las preguntas frecuentes gana en el ranking.
Autoridad de la fuente¿Es este el sistema o el documento que debe decidir la respuesta?Un folleto de ventas antiguo contradice la política legal.
Actualidad de la fuente¿Está vigente la fuente?Se recupera un horario de atención que ya fue sustituido.
Fidelidad de la respuesta¿Se mantuvo el modelo dentro de la evidencia recuperada?El modelo añade una excepción sin respaldo.

4. Estado en vivo y autorizado: cuando la respuesta debe provenir del sistema del negocio

Algunas preguntas no deberían responderse en absoluto a partir de la memoria del modelo ni de documentos estáticos.

La disponibilidad del calendario es un ejemplo claro. La API FreeBusy de Google Calendar devuelve información de disponibilidad (libre/ocupado) para un conjunto definido de calendarios y rangos de tiempo.4 Un agente en producción al que se le pregunta «¿Está libre hoy a las 3 p. m.?» puede usar una herramienta autenticada de la aplicación para consultar el calendario en lugar de inferir la disponibilidad a partir de un documento.

El mismo principio se aplica a:

  • el estado actual de los pedidos;
  • el estado de la cuenta del cliente;
  • los niveles de inventario;
  • el estado de los pagos;
  • los tickets de servicio activos;
  • los precios vigentes cuando cambian de forma dinámica;
  • la disponibilidad actual del personal o de los recursos.

Para estas preguntas, el sistema de origen debe determinar la respuesta. La función del modelo de lenguaje es entender la solicitud de la persona que llama, seleccionar la operación adecuada y explicar el resultado obtenido de forma natural.

Dónde encajan las llamadas a herramientas

Las llamadas a herramientas son el puente entre el modelo y el código de la aplicación. No son lo mismo que RAG, aunque ambos pueden aportar información al modelo.

OpenAI documenta las llamadas a funciones como un intercambio de varios pasos: la aplicación envía las herramientas al modelo, el modelo devuelve una llamada a una herramienta, la aplicación ejecuta código con los datos de entrada de esa llamada, la aplicación devuelve el resultado de la herramienta y el modelo produce entonces una respuesta o solicita herramientas adicionales.2

Persona que llama«¿Hay disponibilidad a las 3 p. m.?»
→
ModeloSolicita get_availability
→
AplicaciónEjecuta código autorizado
→
CalendarioDevuelve el estado actual
→
ModeloExplica el resultado

Esa arquitectura respalda una distinción importante: el modelo puede solicitar una consulta, pero es la aplicación la que la realiza. Esta separación se vuelve aún más importante cuando la herramienta modifica un estado externo. Nuestro próximo artículo sobre las integraciones de agentes de voz con IA trata en detalle las API, los webhooks, las escrituras en el CRM, la reserva de citas en el calendario y la verificación de transacciones.

¿Qué puede fallar en cada capa de conocimiento?

Un agente robusto no debería reducir estos fallos a una única alternativa de respaldo (fallback) como «No lo sé». El comportamiento correcto depende de lo que haya fallado. La ausencia de resultados en el conocimiento puede justificar una alternativa segura o una transferencia a una persona. La consulta en vivo del registro de un cliente puede exigir una nueva autenticación. Un tiempo de espera agotado puede significar que el estado es desconocido, no que sea negativo.

¿RAG evita las alucinaciones?

No. RAG puede mejorar el fundamento de las respuestas al darle al modelo evidencia relevante, pero no garantiza matemáticamente una respuesta correcta.

Todavía pueden fallar varias cosas:

  • el recuperador no encuentra ninguna fuente relevante;
  • el pasaje mejor clasificado no es el autorizado;
  • la propia fuente es incorrecta o está desactualizada;
  • dos fuentes entran en conflicto;
  • los controles de acceso permiten recuperar contenido que la persona que llama no debería recibir;
  • el modelo va más allá de la evidencia recuperada al generar su respuesta.

La guía de OWASP sobre debilidades de vectores y embeddings señala específicamente el acceso no autorizado y la fuga de datos como riesgos de los sistemas RAG cuando los controles de acceso de la capa de recuperación son inadecuados o están mal alineados.5 Esta es una de las razones por las que la arquitectura del conocimiento y la arquitectura de seguridad no pueden diseñarse de forma independiente.

Error frecuente

«Si la recuperación devuelve una puntuación de similitud alta, la respuesta es verdadera». La similitud mide la relevancia respecto a la consulta. No demuestra que la fuente esté vigente, sea la autorizada, esté permitida para esta persona que llama ni que se haya reflejado fielmente en la respuesta generada.

RAG también necesita permisos

Una empresa puede tener un único repositorio de documentos con preguntas frecuentes públicas, procedimientos de empleados, archivos específicos de clientes y material financiero confidencial. Indexarlo todo en un mismo sistema de recuperación no significa que cualquier persona que llame deba poder recuperar cualquier fragmento.

Por eso, la recuperación en producción necesita límites de acceso acordes con el contexto del negocio. Según el sistema, esto puede incluir índices separados, filtros de metadatos, límites por tenant (cliente), recuperación basada en la identidad, permisos a nivel de documento o una capa de aplicación que controle qué fuentes están disponibles en cada sesión.

El modelo de amenazas más profundo —inyección de prompts, mínimo privilegio, datos personales (PII), permisos de herramientas y fuga de datos en RAG— se trata en nuestra guía específica sobre la seguridad de los agentes de voz con IA.

Cómo encajan estas capas en una arquitectura de voz en producción

La ruta del conocimiento se sitúa dentro de la arquitectura más amplia de los agentes de voz que se describe en Cómo funcionan los agentes de voz con IA. Primero, la voz de la persona que llama se convierte en un turno sobre el que el sistema puede razonar. Después, la capa de razonamiento decide qué fuente de información es la adecuada para la pregunta.

La arquitectura es considerablemente más segura cuando el sistema puede explicar internamente —no necesariamente en voz alta en cada llamada— de dónde salió una respuesta. Esa trazabilidad del origen permite depurar, evaluar y tomar decisiones de política que son imposibles cuando toda respuesta se trata como «el modelo lo sabía».

Por qué una ventana de contexto más grande no elimina el problema de la recuperación

Los modelos actuales pueden aceptar grandes cantidades de contexto, lo que puede hacer tentador cargar en cada llamada un manual completo de la empresa, un catálogo de productos y un archivo de políticas. Un contexto amplio puede ser útil, pero no elimina las cuestiones de arquitectura que RAG está diseñado para resolver.

En primer lugar, un contexto amplio no resuelve automáticamente la selección de la fuente. Si el prompt contiene varias versiones de la misma política, el modelo todavía tiene que determinar cuál es la autorizada. En segundo lugar, no resuelve automáticamente la actualidad de los datos. Un prompt largo puede contener datos desactualizados con la misma facilidad que un almacén vectorial. En tercer lugar, puede complicar los permisos si cada sesión recibe información a la que la persona que llama nunca debería acceder. Por último, cargar material innecesario en cada turno puede aumentar el costo y la complejidad.

Por estas razones, «RAG vs. contexto largo» no es una cuestión en la que haya un único ganador. La decisión práctica es qué información debe estar presente por defecto y cuál debe obtenerse solo cuando sea relevante. Las instrucciones globales estables pueden pertenecer al contexto; las colecciones de conocimiento grandes o con permisos pueden recuperarse mejor de forma selectiva.

¿Qué debe ocurrir cuando la recuperación no encuentra nada?

Un agente en producción necesita una política explícita para los casos sin resultados. Si la recuperación devuelve evidencia débil o vacía, el agente no debe convertir en silencio la incertidumbre en seguridad.

Entre los comportamientos seguros posibles están hacer una pregunta aclaratoria, probar otra consulta de recuperación, cambiar a un sistema en vivo cuando la pregunta es en realidad transaccional, dar una respuesta limitada que refleje con claridad la evidencia disponible o escalar el caso a una persona. La alternativa de respaldo (fallback) adecuada depende del riesgo para el negocio.

El mismo principio se aplica cuando las fuentes entran en conflicto. Si dos documentos se contradicen, el sistema debe tener una regla de autoridad —como el estado del documento, la fecha de entrada en vigor, el departamento responsable o una fuente de verdad designada— en lugar de pedirle al modelo de lenguaje que adivine qué política «suena» más plausible.

Nota de ingeniería

Los fallos de recuperación deben ser observables. Registre si la respuesta provino del contexto del prompt, de una fuente recuperada o de una herramienta en vivo, y guarde los metadatos suficientes para reproducir los casos débiles o sin resultados sin exponer innecesariamente contenido sensible.

Atribuir la fuente es útil aunque la persona que llama nunca escuche una cita

Normalmente, quien llama por teléfono no quiere escuchar una bibliografía después de cada respuesta. Sin embargo, el backend sí puede conservar la procedencia: qué fragmento de documento se recuperó, qué herramienta devolvió el estado actual, qué ID de registro se usó y qué versión de la fuente estaba activa.

Esa trazabilidad ofrece varios beneficios operativos. Facilita la depuración de las respuestas erróneas, respalda las pruebas de regresión tras una actualización de la base de conocimiento y ayuda a separar los problemas de generación del modelo de los problemas de los datos de origen. Si un agente da una respuesta desactualizada, los equipos pueden determinar si el recuperador seleccionó el documento equivocado, si el índice contenía contenido obsoleto o si el modelo ignoró evidencia correcta.

Esta es otra razón para evitar la frase vaga «la IA lo sabía». En los sistemas en producción, la procedencia debe poder inspeccionarse aunque sea invisible para la persona que llama.

¿Qué deben evaluar los equipos?

Las pruebas de conocimiento no deben limitarse a «el agente respondió correctamente una vez». Un conjunto de evaluación útil debe probar por separado el comportamiento de cada capa de fuentes:

  • preguntas que deben responderse a partir del contexto estable del prompt;
  • paráfrasis semánticas de la misma pregunta sobre una política;
  • consultas para las que la base de conocimiento no contiene respuesta;
  • documentos vigentes y obsoletos que se contradicen;
  • preguntas sobre estado en vivo cuyas respuestas cambian entre una ejecución de prueba y otra;
  • consultas exactas de clientes con nombres o ID similares;
  • pruebas de permisos sobre documentos que deben ser inaccesibles;
  • fallos de herramientas y tiempos de espera agotados;
  • comprobaciones de que las respuestas generadas se mantienen fieles a la evidencia devuelta.

Mantener claros estos límites evita que «RAG», «herramientas» e «integraciones» se conviertan en sinónimos imprecisos.

Preguntas frecuentes

¿Cómo conoce un agente de voz con IA mi negocio?

La información del negocio puede suministrarse mediante el contexto del prompt o de ejecución, recuperarse de una base de conocimiento o leerse de sistemas de negocio en vivo, como un CRM o un calendario. La fuente adecuada depende de si la información es estable, documental, privada o sensible al tiempo.

¿Qué es RAG en la IA de voz?

RAG recupera información relevante de fuentes de conocimiento externas y se la proporciona al modelo como contexto antes de que responda. La recuperación semántica puede encontrar pasajes conceptualmente relacionados aunque la persona que llama use otras palabras.

¿Cuál es la diferencia entre RAG y una consulta por API?

RAG suele resolver un problema de relevancia: ¿qué documento o pasaje ayuda a responder esta pregunta? Una consulta por API puede leer un registro actual específico de un sistema externo autorizado. Las preguntas sobre políticas suelen encajar con RAG; la disponibilidad en vivo y el estado del cliente suelen encajar con las API.

¿RAG evita las alucinaciones?

No. RAG puede mejorar el fundamento de las respuestas, pero el contenido recuperado puede faltar, estar desactualizado, ser contradictorio, no estar autorizado o interpretarse mal. Es una capa de control de la veracidad, no una garantía.

¿Cómo sabe un agente de IA la disponibilidad del calendario?

Un agente en producción puede consultar el estado actual del calendario mediante una herramienta o una API autenticada. La API FreeBusy de Google Calendar es un ejemplo de un punto de acceso de un sistema de origen que devuelve información de disponibilidad (libre/ocupado) para calendarios y rangos de tiempo definidos.

¿Un agente de voz con IA conoce automáticamente mi CRM?

No. El acceso al CRM requiere una integración, credenciales, permisos y lógica de aplicación. El modelo solo puede usar los datos privados del CRM que el sistema que lo rodea esté autorizado y diseñado para proporcionar.

¿Cuándo deben usarse herramientas en vivo en lugar de RAG?

Las herramientas en vivo suelen ser la mejor fuente cuando la respuesta depende del estado operativo actual, de un registro privado exacto o de una acción externa. RAG suele ser más adecuado para recuperar conocimiento explicativo de documentos.

La pregunta importante no es «¿La IA lo sabe?»

La mejor pregunta es: ¿Qué fuente produjo esta respuesta y es esa fuente la autorizada para esta pregunta?

El conocimiento del modelo, el contexto del prompt, RAG y los sistemas de negocio en vivo resuelven problemas distintos. Un agente de voz fiable los usa de forma deliberada. Las instrucciones estables pueden vivir en el contexto. La documentación extensa puede recuperarse. El estado actual del negocio debe provenir del sistema que lo gestiona. Las acciones externas deben ejecutarse y verificarse mediante herramientas controladas.

Esa separación es la base de la siguiente capa de la arquitectura de producción: cómo se conectan los agentes de voz con IA a las API, los CRM, los calendarios y los sistemas de flujo de trabajo.

Fuentes técnicas y base de investigación

Los comportamientos específicos de cada proveedor se presentan como ejemplos y no como estándares universales. Los marcos de ingeniería de este artículo son modelos editoriales de B2B Voice elaborados a partir de las fuentes primarias y los estudios citados.

  1. OpenAI — Retrieval. Documentación oficial sobre búsqueda semántica, almacenes vectoriales, fragmentos relevantes, puntuaciones de similitud y archivos de origen.
  2. OpenAI — Function calling. Documentación oficial que muestra el ciclo de vida de las llamadas a herramientas entre el modelo y la aplicación, y la ejecución en el lado de la aplicación.
  3. Microsoft — Configure freshness-aware retrieval in Azure AI Search. Documentación oficial que ilustra la actualidad de los datos como un aspecto independiente del ranking de recuperación; la función citada es una implementación en versión preliminar de Microsoft.
  4. Google — Calendar API FreeBusy. Referencia oficial para consultar la información actual de disponibilidad (libre/ocupado) de los calendarios.
  5. OWASP GenAI Security Project — Vector and Embedding Weaknesses. Guía de seguridad sobre los riesgos de RAG y de los vectores, incluidos el acceso no autorizado y la fuga de datos.
